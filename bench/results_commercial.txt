IGAOS against CPLEX and Gurobi
==============================

Measured 28 Aug 2026, aarch64 Linux, GCC 11, two cores.  Reproduce with

    ./bench/fetch_benchmarks.sh            # creates benchmarks/standard
    pip install cplex gurobipy
    python3 bench/commercial.py --dir benchmarks/standard --time-limit 60

(The first line used to be missing and the directory it names did not exist --
defect 22.  A number nobody else can reproduce is a claim, not a measurement.)

The IGAOS times below are with the branch-and-cut tree running on both of this
machine's cores, which is the default; see bench/results_parallel.txt.  They are
roughly half what the same table showed when the tree was serial.  The commercial
solvers were on the same two cores.

Until this run every comparison in the project was against open source, because
the team had no commercial licence.  Two of the three solvers PS 26119 names
ship a free size-limited licence of the real product:

    CPLEX Community Edition    1000 rows x 1000 columns
    Gurobi restricted licence  2000 rows x 2000 columns

THE CAVEAT, FIRST
-----------------
Those limits cap every instance below at a size where a mature commercial solver
has almost no room to show its advantage.  Nothing here supports any claim about
how IGAOS behaves at industrial scale against CPLEX or Gurobi.  It supports one
claim, and it is the claim that was missing until now: THE ANSWERS AGREE.

Both commercial solvers were run with their MIP gap tightened to 1e-9.  Left at
the default 1e-4 they stop early and report a suboptimal incumbent as "optimal",
which produced two false disagreements on the first run of this harness --
dcmulti and gesa2.  That was a defect in the comparison, not in any solver, and
it is recorded here because it is exactly the kind of mistake that turns into a
false claim if nobody re-runs it.

THE ONE DISAGREEMENT
--------------------
bell5.  IGAOS returns 9,032,233.9 at 60 s and reports status FEASIBLE -- not
optimal.  CPLEX and Gurobi both prove 8,966,406.5 in under a tenth of a second.

Given 300 seconds instead of 60 it gets to 8,988,498.5: 0.25% above the true
optimum and still not closed.  This is not a wrong answer.  It is an unfinished
one, correctly labelled, and bell5 was already the known failure in
results_milp.csv.

The incumbent bell5 reports at a given time limit MOVES between runs now, because
the tree is parallel and which subtree opens first is not deterministic.  Three
different figures appear in this repository's history for the same instance --
9,065,322 / 9,032,234 / 8,988,498 -- and all three are honest readings of an
unfinished search.  bench/results_parallel.txt says the same thing at more
length: what a parallel tree is allowed to change is the incumbent at a limit,
never the answer at optimality.

WHAT THIS DOES NOT SAY
----------------------
Look at the timings and the honest reading is plain: on mixed-integer models
IGAOS is between one and three orders of magnitude slower than either commercial
solver.  gt2 takes 60 seconds here and 0.01 seconds in CPLEX.  bell5 it does not
finish at all.  Putting the tree on both cores roughly halved these times and
changed nothing about that conclusion -- a 2x is not a 1000x.

That gap is thirty years of engineering, and no run in this file narrows it.
What the file establishes is that where IGAOS finishes, it finishes at the same
answer as CPLEX and Gurobi -- 34 agreements, 0 wrong answers -- which is the
prerequisite for everything else, and which the project could not previously
claim at all.
